# Cursor 会话与提示词（控用量 · 提交付密度）

> 挂接：[ai-native-daily · Vibe 四步](ai-native-daily.md) · 培训手册「任务原子化」· [mindset-角色大前提](mindset-角色大前提.md)（前端叠加见 [frontend prompts/mindset](../../frontend-dev-spec/references/prompts/mindset-角色大前提.md)）  
> 原则：**贵模型留给可验收增量**；额度浪费多半来自长会话与全量任务，不是「某一句写砸了」。

---

## 1. 硬规矩（人 + Agent 共守）

| #   | 规矩                                                                               | 反例                                             |
| --- | ---------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1   | **一事一会话**：一 Plane Issue / 一可验收增量 ≈ 一 Cursor 聊天窗口                 | 同一窗口从调研→多仓改造→提交→再扩 scope 连打几天 |
| 2   | **验收 ≤5 条**；一句话说清「本轮只做什么」                                         | 「把 IAM/齐套/所有接口/循环验证全搞完」          |
| 3   | **新需求 / 新仓 / 新 Plan 落地 → 新开聊天**；旧窗只收尾                            | 在 100+ 轮会话里继续「Implement the plan」       |
| 4   | **禁止用「继续 / 需要 / 确认」续命超长上下文**；改写收口指令（见 §3）              | 挂着整段历史只回「继续」                         |
| 5   | **提交 / push / Plane 闭环单独短会话**（或本轮最后一句且声明「只交付、不改代码」） | 开发长上下文末尾叠整套 `@da` 闭环                |
| 6   | **日常问答用 Auto / 轻量模型**；Composer / 高端模型留给多文件改造                  | 所有闲聊、查字段都开最贵模型                     |
| 7   | **齐套 / 循环验证拆勾选**：先声明「本轮只验 A」；下轮再 B                          | 一句触发多仓 + 全套 skill + 多子代理             |
| 8   | **违规/过长必须提示用户**（见 §1.1）；禁止静默继续高耗路径                         | 明知超长或不合规仍闷头探索/Implement             |

### 1.1 强制提示（Agent 硬约束 · 不可省略）

命中下表任一条件时，**本轮回复开头**（在 mindset 开场句之后、动手工具之前）必须给出可见提示；**禁止**只在内心判断、不写给用户。提示须含：**问题类型 + 一句理由 + 建议动作**（新开聊天 / 收窄本轮 / 补全收口句）。用户明确回复「仍在本窗继续」后，才可在本窗最小范围执行，且仍应在当轮首句复述边界。

| 触发（满足其一即提示）                                                          | 建议动作                                 |
| ------------------------------------------------------------------------------- | ---------------------------------------- |
| 本会话用户轮次偏多（经验阈值：**≥30 轮**用户消息，或同窗已多次 Plan→Implement） | 建议**新开聊天**承接新增量               |
| 同窗已跨 **≥2 个业务仓**、或从调研/文档跳到另一大功能                           | 建议新开窗，或声明「本轮只收尾旧仓」     |
| 用户只回「继续 / 需要 / 确认 / 好」且无路径+验收                                | 请补 §3.2 收口句，或 AskQuestion         |
| 用户说「全部 / 所有 / 齐套 / 循环验证」且未写「本轮只…」                        | 收窄为一项，或拆轮                       |
| 超长开发窗上直接「提交 / push / 同步 Plane」且未声明只交付                      | 建议**短会话只交付**，或声明不改业务代码 |
| 提示词无「本轮只做 / 路径 / 验收」的模糊大单（「帮我弄一下」「都改掉」）        | 请补 §3.1，或 AskQuestion 收口           |

**固定话术骨架**（可微调，不可省略结构）：

```text
⚠️ 会话提示：<过长 | 不合规：缺边界/全量未拆/空转续聊/…>
理由：…
建议：① 新开聊天做「…」；或 ② 本轮收窄为「只…」（验收：…）。
请选 ① / ②；选 ② 请确认后我再动手。
```

**禁止**：命中上表却不提示；提示后不等用户确认就扩 scope / 拉满子代理 / 第二次大 Implement。

## 2. 高耗操作（按贵→便宜）

1. **百轮长会话**（后期每句都拖整段历史）
2. **同窗反复 Plan → Implement the plan**
3. **并行 explore / 多子代理 + 「very thorough」**
4. **跨多 `repos/` + 大 `@文件` + 多图** 且无「只改路径」边界
5. **交付闭环**（scan / commit / timeline / WorkRecord）叠在开发长上下文上

优先砍 1–3，额度下降最明显。

## 3. 人侧提示词模板

### 3.1 开发（推荐）

```text
【本轮】只做：<一句话>
【仓/路径】<repo 或目录>；禁止动：<路径或「其他仓」>
【输入】…
【输出】…
【约束】最小 diff；不顺手重构
【验收】1. … 2. …（≤5）
【模型】多文件改动用 Agent；纯问答可 Autocomplete/轻量
```

### 3.2 续做（替代「继续」）

```text
【续】仅改 <文件或符号>：<具体改动>
【不要】扩 scope / 重搜全仓 / 新开子代理
【验收】…
```

### 3.3 齐套 / 验证（拆轮）

```text
【本轮只验】<清单中的一项，如：S3 权限码表与菜单>
【不做】其他仓 / 全量循环验证 / 提交
【产出】差距表 ≤10 行 或 最小补丁
```

### 3.4 提交（短会话）

```text
【只交付】当前 Focus <Task ID>；不改业务代码
提交 → timeline-sync → task done → WorkRecord → pm sync
```

## 4. Agent 接到任务时的默认行为

0. **先跑 §1.1 触发表**：命中 → **先写 ⚠️ 会话提示**（再 AskQuestion / 等确认）；未命中再进入下列步骤。
1. **复述本轮边界**（一句话 + 验收 ≤5）；范围过大 → AskQuestion 收窄或建议新窗（须可见，不可只做不说）。
2. **能 grep/读指定文件则不启动 explore 子代理**；禁止无必要 `very thorough`。
3. **禁止**在同一回复为「顺便」拉起多个无关子代理。
4. 用户说「继续」且会话已很长 → **必须先 §1.1 提示**，再请补 §3.2；仅当用户确认「本窗最小下一步」后才执行，并明示假设。
5. Plan 已确认：一次落地到可验收；改需求则 **提示并建议新开 Implement 会话**，勿在原窗静默叠第二次大 Implement。
6. 触发 frontend/backend/da skill 时：**按任务只读必要 reference**，勿一次读完整个 skills 树（与 frontend-dev-spec「勿一次全读」一致）。

## 5. 自检（开聊前 10 秒）

- [ ] 本窗是否仍是「同一可验收增量」？否则新开（Agent：**须提示用户**）
- [ ] 提示词是否含路径边界 + 验收，而非只有「帮我弄一下」（否则 **须提示**）
- [ ] 是否误开最贵模型做问答
- [ ] 「全部/齐套」是否已拆成「本轮只…」（否则 **须提示**）
- [ ] 提交是否准备新开短窗（长窗上提交 → **须提示**）
- [ ] §1.1 若命中：本轮是否已写出 ⚠️ 会话提示（未写 = 违规）

## 6. 常驻面预算（rules / skill description）

额度浪费多半来自 **每轮注入**，不是 references 磁盘体积。维护 `.cursor` 时遵守：

| 层                         | 预算                                                | 写法                                                                    |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------- |
| always rules               | 只放红线与触发指针；仓内 always 正文合计宜 ≤~120 行 | 安全 / vibe / 项目上下文 / timeline 指针；禁止把整份交付手册贴进 always |
| skill `description`        | **≤400 字**；只列触发词 +「细则见 references」      | 禁止把 IAM 齐套、组件映射、门禁全文塞进 YAML frontmatter                |
| skill 正文 + `references/` | 深度 SSOT，**按需 Read**                            | 命中 skill 后只读本任务相关 reference，勿一次读完树                     |

**双轨**：

- **项目 skill**（frontend / backend / da-workflow / 文档与报表）：改 **marsun_arch**，再 sync 到 repos（见 [skills-sync.md](skills-sync.md)）。
- **全局 CLI / hooks / 用户级 thin rules**：改 team-sync 源后 `da install-config`；本机手改可能被下次 install 覆盖。
- **禁止** `~/.cursor/skills/<同名>` 与项目各维护一份长 description；全局同名只留 stub。
